# [Project Name] Message Foundation — required structure

Every Message Foundation document must contain the sections below, in this order. Notes under each define what "complete" looks like — use them to self-check before finalizing, not just to fill space.

## 0. Overview

One paragraph: what the project is, what this document is for, and who should use it (anyone writing web copy, social, campaigns, or talking to press/members about the project). Note the source date and, if a Brand Kit exists, that this document is derived from it.

## 1. Project Definition

- **What it is** — 1–2 sentences, jargon-minimal, grounded in the README/brand kit, not marketing fluff.
- **Elevator pitch (long, ~60-90 words)** — usable standalone, a reader gets it with no other context.

## 1a. Word-Count Derivatives (when a Brand Kit exists)

Per the LFX Marketing OS document architecture (Brand Kit → Message Foundation Doc → ICP Document), when a project already has a Brand Kit, this agent's core job is producing these exact derivative assets *from* it, not re-deriving positioning/voice from scratch:

- **25-word summary** — hard cap, standalone.
- **50-word summary** — hard cap, standalone, slightly more context than the 25-word version.
- **Boilerplate** (~100-150 words) — press-release-footer style: what it is, who governs it, license, where to learn more.
- **llms.txt** — following the llms.txt convention (H1 project name, one-line blockquote summary, then linked sections for docs/downloads/community/repo) so AI crawlers and agents get an accurate, structured summary.
- **Elevator pitch slide** — a single slide's worth of content: headline (≤10 words), 3-4 supporting bullets, one proof point, one CTA.

If no Brand Kit exists, skip this section's "derived from" framing and instead build these five assets directly from the interview answers and README — same five deliverables, just sourced differently.

## 2. Voice & Tone

- Three (or the user's) voice adjectives, each with one line on what it means in practice (pull directly from the Brand Kit if one exists).
- A short "Do / Don't" list (5-8 items) translating those adjectives into writing behavior, ideally with a "sounds like / doesn't sound like" example pair per adjective.
- Reading-level guidance if relevant (e.g., "don't write above an 8th-grade level for external audiences").

## 3. Positioning Statement

Single-sentence formula: **For [primary audience] who [need/problem], [Project] is the [category] that [key benefit] — unlike [alternative/status quo], [key differentiator].**
Fill "unlike" honestly; if the user didn't name a real alternative, mark that clause TBD rather than inventing a strawman.

## 4. Unique Value Proposition

- One paragraph UVP.
- 2-3 short/tagline-style alternates suitable for event signage or a hero headline, clearly labeled as options, not a final decision.

## 5. Target Audiences

One entry per audience segment named by the user (or clearly inferable from the README/Brand Kit). For each: **Titles/roles**, **Problem** (the thing keeping them up at night, in their words not ours), **Concerns/objections**, **Core message**, **Sample CTA**. If the interview surfaced multiple outreach objectives (e.g. awareness, membership sales, event attendance/sponsorship, education sales), add an **Outreach Objective → Primary Audience → Angle** mapping table so the document is directly actionable for campaign planning, not just descriptive.

## 6. Messaging Pillars

3-5 pillars max. For each: a short name/headline, 2-4 sentences of supporting narrative, and at least one **proof point** (a real stat, adopter, milestone, or technical fact — not "many organizations trust us" without a number or name). If a pillar has no real proof point yet, say so explicitly rather than writing a vague one. If the user has flagged specific proof points as unconfirmed or off-limits (e.g. can't name a customer), use generic-but-verifiable alternatives (community/repo metrics, license terms, governance facts) instead.

## 7. Value Messages, Support Points & Proof Points

A structured list: **Value message** (a single claim, e.g. "We reduce operational risk") → **Support points** (2-3 reasons that back the claim) → **Proof points** (the evidence — numbers, named adopters, benchmarks, third-party validation, or the generic-but-verifiable substitute per Section 6).

## 8. Talking Points & Soundbites

- **Executive soundbite** — one quotable sentence for a keynote or exec quote.
- **Short/social message** — one paragraph sized for a social post or newsletter blurb.
- **Audience-specific angles** — one line each for the audiences in Section 5, translating the core message into what that specific audience cares about.

## 9. Terminology, Constraints & Differentiation

- Naming conventions (correct project name usage, capitalization, "the [X] project" vs. bare name).
- Anything to avoid (colors/marks, trademark concerns, LF-family consistency notes, named-competitor restrictions) — pull directly from the brand kit or the user's constraint answer.
- Reference brands/projects named as admired or to differentiate from, and one line on what's being borrowed vs. avoided from each.

## 10. Next Steps

One short paragraph naming what this document is the input for (web copy, social bios, press boilerplate, campaign briefs, sales one-pagers) and a reminder that those are separate, follow-on requests — this document is the foundation, not the finished asset.

## Appendix: Interview Record

Raw decisions/answers collected during the session, for traceability — mirrors any companion Brand Kit's own source-intake appendix, so the document family stays consistent.

---

### Section-completeness self-check (apply before finalizing)

Every fact in Sections 1, 1a, 3, 6, and 7 must trace to: the user's interview answers, the project's Brand Kit, or the GitHub README. Anything else gets written as **TBD — needs input**, never smoothed over with generic language.
